# 신뢰성 확인 쿼리 3개 (쉬운 설명)

**한 줄:** 조사 에이전트가 원인을 찾기 전에 "이 장부를 믿어도 되나?"를 확인하는 3가지 질문(쿼리)이다.

| # | 질문 | 어떻게 확인하나 | 결과 읽는 법 |
|---|---|---|---|
| Q1 누락 | 메시지가 빠졌나? | 파티션 안에서 offset은 0,1,2,…로 이어져야 한다. "처음~끝 칸 수 − 실제 줄 수"가 빠진 개수다 | 0줄이면 **관측된 범위 안에 빈 곳이 없다**는 뜻이다(전체가 다 있다는 뜻은 아니다, 아래 한계) |
| Q2 중복 | 같은 것이 두 번 쌓였나? | **메시지 위치(토픽, 파티션, offset)가 같은 줄**을 센다(`topic_messages`). 결제 번호가 같은 줄(`payment_events`)은 참고로만 센다 | 메시지 위치 중복이 0이면 정상. 0보다 크면 **적재 쪽 문제**. 결제 번호 중복은 Debezium 재시작·전송 재시도로 생기는 정상 현상이라 뷰가 걸러 주므로 문제로 보지 않는다 |
| Q3 멈춤 | 장부를 쓰는 잡과 지연 수집기가 살아 있나? | 마지막으로 쓴 시각이 2분 넘게 지났는지 본다(은서 님 문서의 고장 기준) | STOPPED면 "데이터 이상"이 아니라 "관제 고장"으로 따로 표시. 표가 비어 있으면 **NO_DATA**(정상 아님) |

## 비유
택배 상자에 1번부터 번호가 붙어 있을 때, **번호가 빠졌는지(Q1)**, **같은 번호가 두 장 있는지(Q2)**, **접수 직원이 아직 일하고 있는지(Q3)** 를 먼저 확인하는 것과 같다.

## 시험 결과
가짜 장부에 누락 3개, 메시지 중복 5개, 결제 중복 4개를 심고 돌려서 모두 찾았다(결제 중복은 참고값이다). 정상 장부에서는 0으로 나왔다. Q3는 2분 기준(120초는 정상, 180초는 고장)을 확인했다.

## 한계 (솔직하게)
- **Q1이 0줄이어도 전체 데이터가 있다는 뜻이 아니다**(재영 님 리뷰). Q1은 관측된 가장 작은 offset과 가장 큰 offset 사이의 빈 곳만 찾는다. 구간 맨 앞·맨 뒤 메시지나 **파티션 전체**가 빠지면 찾지 못한다. 보완으로 Q1b(구간 안에 메시지가 있는 파티션 목록)를 예상 파티션 목록과 비교하고, 완전성은 Kafka 끝 offset과 비교해야 확인할 수 있다(아직 안 했다). 그래서 이 점검은 "빠진 곳이 보이면 알려 주는 것"이지 "전체가 다 있음"을 증명하지 않는다.
- Q3는 **표가 비어 있으면 OK가 아니라 NO_DATA**로 표시한다(이전에는 마지막 시각이 NULL이어서 OK로 나왔다).
- 시험은 **sqlite로 했고 Athena에서는 아직 돌려 보지 않았다.** 문법이 조금 다를 수 있다(예: 문자열 이어 붙이기).
- Q3의 시각 계산은 **같은 기준을 파이썬으로 시험**했고, Athena의 `date_diff`·`current_timestamp`는 실제 환경에서 확인해야 한다.
- 만약 Kafka가 트랜잭션을 쓰면 offset에 정상적인 빈 곳이 생길 수 있다. 은서 님 파이프라인은 일반 메시지라서 해당 없을 가능성이 크지만 확인이 필요하다.

- **Q3 멈춤 확인의 약점 두 가지.**
  - 원장 적재 잡은 메시지가 올 때만 줄을 쌓는다. 메시지가 2분 넘게 안 오면 잡이 멀쩡해도 `STOPPED`로 보일 수 있다. 반면 지연 수집기는 데이터가 없어도 1분마다 돌므로(Gold B 문서) 이쪽이 더 믿을 만한 생존 신호다.
  - `MAX(loaded_at)`를 표 전체에 걸면 비용이 커진다. 실제로 쓸 때는 최근 시간 폴더(`dt`, `hour`)만 읽도록 범위를 좁혀야 한다.

## 실행

```
cd agent/reliability
python3 test_reliability.py     # sqlite 가짜 장부로 3개 쿼리 시험 (표준 라이브러리만 사용)
```

쿼리 본문은 `reliability_queries.sql`이다. 테이블 이름은 `gold_b.topic_messages`, `gold_b.payment_events`, `gold_b.bronze_lag_snapshots`를 가정한다.
