# agent/prototype

탐지 규칙(R1~R4)을 **가짜 데이터**로 시험하는 프로토타입이다. 실제 Athena나 Kafka에 연결하지 않는다.

## 실행

```
cd agent/prototype
python3 evaluate_v3.py      # 규칙 설정별 탐지율·오탐·걸린 시간 표 (표준 라이브러리만 사용)
```

## 파일

| 파일 | 역할 |
|---|---|
| `sample_data.py` | 사건 3개(PG 장애, 소비 지연, 스키마 오염)와 주문·메시지 생성 |
| `ledger_v3.py` | 1분 단위 원장 모양의 가짜 데이터 생성 |
| `detect_v3.py` | 규칙 R1(PG 원인 실패), R3(소비 지연), R4(깨진 메시지) 판정 |
| `evaluate_v3.py` | 30회 반복 시험과 결과 표 |
| `modes.py` | 시연 모드(일상·중간 3배·폭주 10배)별 탐지 시간 시험 |
| `REPORT.md` | v3 시험 보고서 |

## 모드별 결과 (`python3 modes.py`, 판정 5분마다, 가짜 데이터 30회)

시뮬레이터 확률표(2026-10-16)의 분당 주문 수를 하루로 환산해 넣었다. 걸린 시간은 장애 시작부터 규칙이 이상으로 판정할 때까지의 분(평균 / 최대)이다. 사건 2·3은 모든 조건에서 5 / 5였고(판정이 5분마다 돌아 5분 단위로 나온다), 아래 표는 사건 1 PG 장애와 오탐만 적었다.

세 가지 조건을 비교한다.
- (가) 평소 PG 원인 실패 **0**, R1 = 최근 15분 PG 원인 실패 3건 이상 (옛 가정)
- (나) 평소 PG 원인 실패 **1.15%**(확률표 값), R1 = 3건 이상 → 오탐이 늘어난다
- (다) 평소 PG 원인 실패 1.15%, R1 = **3건 이상 + 그 PG 결제 시도 중 PG 원인 실패 비율 20% 이상** (제안)

| 모드 (분당 주문) | (가) PG 장애 / 오탐 | (나) PG 장애 / 오탐 | (다) PG 장애 / 오탐 |
|---|---|---|---|
| 일상 새벽 (0.7) | 11 / 20분, 0.03 | 11 / 20분, 0.77 | 11 / 20분, 0.03 |
| 일상 하루평균 (하루 5,000건) | 5 / 5분, 0.03 | 4 / 5분, 4.00 | 5 / 10분, 0.03 |
| 일상 저녁 피크 (6.3) | 5 / 5분, 0.03 | 5 / 5분, 10.17 | 5 / 5분, 0.03 |
| 중간 (19) | 5 / 5분, 0.07 | 의미 없음, 56.43 | 5 / 5분, 0.07 |
| 폭주 (63) | 5 / 5분, 0.03 | 의미 없음, 18.97 | 5 / 5분, 0.03 |

(오탐은 하루당 건수. (나)의 "의미 없음"은 장애 전에 이미 울려서 걸린 시간이 음수가 된 경우다.)

**(다)에 비율 규칙의 3분 대기를 더하면** (Gold B 문서: 비율 규칙은 구간이 끝난 지 3분 지난 것만 판정). 원장에 보이기까지 1분이 아니라 3분 걸린다고 두고 쟀다.

| 모드 (분당 주문) | 사건 1 PG 장애 (평균 / 최대) | 사건 2 소비 지연 | 사건 3 스키마 오염 | 오탐(하루) |
|---|---|---|---|---|
| 일상 새벽 (0.7) | 13 / 20분 | 5 / 10분 | 6 / 10분 | 0.07 |
| 일상 하루평균 (하루 5,000건) | 7 / 10분 | 5 / 5분 | 5 / 5분 | 0.00 |
| 일상 저녁 피크 (6.3) | 7 / 10분 | 5 / 5분 | 5 / 5분 | 0.00 |
| 중간 (19) | 8 / 10분 | 5 / 5분 | 5 / 5분 | 0.03 |
| 폭주 (63) | 8 / 10분 | 5 / 5분 | 5 / 5분 | 0.00 |

**약한 장애** (장애 동안 PG_A 결제 실패율을 낮춰 사건 1만 시험, 3분 대기 적용, 30회 중 탐지 횟수 / 걸린 시간 평균·최대 분)

| PG_A 실패율 | 일상 새벽 | 일상 하루평균 | 일상 저녁 피크 | 중간 | 폭주 |
|---|---|---|---|---|---|
| 90% | 30/30, 13/20 | 30/30, 7/10 | 30/30, 7/10 | 30/30, 8/10 | 30/30, 8/10 |
| 50% | 27/30, 20/30 | 30/30, 11/15 | 30/30, 11/15 | 30/30, 10/15 | 30/30, 10/10 |
| 30% | 17/30, 23/30 | 30/30, 15/25 | 30/30, 14/20 | 30/30, 14/15 | 30/30, 15/15 |
| 20% | 9/30 | 23/30 | 22/30 | 25/30 | 27/30 |
| 10% | 2/30 | 9/30 | 2/30 | 0/30 | 0/30 |

- 실패율이 낮을수록 늦게 잡히고, **20% 이하에서는 일부를 놓친다.** 비율 기준 20% 때문이다. 약한 장애도 잡으려면 기준을 낮춰야 하는데, 그러면 평소 PG 실패(1.15%)와 구별이 어려워 오탐이 늘어난다(10%: 하루평균에서 오탐 약 1.2건, 1분 반영 기준). 어느 정도 약한 장애까지 잡을지는 팀이 정한다(**미정**).

- 주문이 많을수록 평소 PG 원인 실패도 15분에 3건을 쉽게 넘어서, 고정 건수 기준은 (나)처럼 오탐이 크게 늘어난다. **비율 조건을 더하면(다) 모든 모드에서 30회 모두 탐지하고 오탐이 하루 0.03~0.07건으로 돌아온다.** 비율 기준 20%는 시험으로 정한 **제안값**이다(10%는 하루평균에서 오탐 1.2건, 30%는 탐지가 늦어짐).
- 기본 시험의 PG 장애는 한 PG의 실패율이 90%인 장애다. 약한 장애는 아래에 따로 적었다.
- 이 프로토타입은 하루 내내 같은 주문 속도라고 가정한다. 실제 일상 모드는 시간대 곡선을 따른다(새벽 분당 0.7 ~ 저녁 6.3).
- 사건 2는 프로토타입에서 평소의 20배 유입 급증이라 시뮬레이터의 폭주 모드와 정의가 다르다.

## 읽을 때 주의

- `python3 evaluate_v3.py`가 기본으로 보여 주는 표는 **판정을 1분마다 돌린 경우**(`step=1`)다. 팀이 제안한 판정 주기는 5분이라서, 5분 주기 결과는 `kw=dict(step=5)`로 따로 재야 한다. 같은 규칙(R1 최근 15분 3건 이상)으로 쟀을 때 PG 장애 탐지는 5분마다 판정하면 하루 900건 평균 13분(최대 30분), 하루 3,600건 평균 5분(최대 10분)이다.
- 위 모드별 결과는 시뮬레이터 확률표의 **제안값**(하루 주문 약 5,000건, 확정 필요)을 기준으로 한다. 하루 900건을 가정했던 옛 시험은 `evaluate_v3.py`의 기본 표에 남아 있다.
- `evaluate_v3.py`의 허용 지연 값(20/7/7분)은 옛 기준이라 확정값이 아니다. 허용 지연은 팀에서 정한다.
