# 이상 이력(anomaly)과 정답표(incident_log) 설계 (초안)

> 작성: 6단계(탐지·에이전트) · 상태 표현: **결정 / 제안 / 미정** (`CLAUDE.md`의 규칙)
> 기준: Gold B 담당자의 「Gold B 칼럼 구성」(2026-10-18 백업), 시뮬레이터 「확률표」(2026-10-16 14:43), 정답표 담당자와 나눈 답변(2026-10-16). 그 문서가 바뀌면 이 문서도 바뀐다.
> 이 문서는 예전 초안 두 개(정답표 초안, 이상 이력 컬럼 초안 v2)를 하나로 합치고 최신 구조에 맞춘 것이다.

## 1. 한 줄 요약

Gold B는 사실을 한 줄씩 쌓는 **원장 4개와 정리 뷰 2개**를 만든다. 탐지 잡은 5분마다 이것을 읽어 구간으로 묶어 세고, 이상을 `gold_b.anomaly`에 **회차(run)별로 쌓는다.** 시뮬레이터는 주입한 장애를 `ground_truth/incident_log/`에 JSON으로 남기고, 이 정답표로 탐지와 조사 결과를 채점한다.

## 3. 지표 이름 대응표 (탐지 규칙이 읽는 이름 → 실제 원장·뷰)

규칙 코드는 왼쪽 이름만 읽고, 오른쪽과의 연결은 이 표(설정)에서 한다. 원장 컬럼 이름이 바뀌면 이 표만 고친다.

| 지표 이름 | 읽는 곳 | 계산 방법 |
|---|---|---|
| `attempts` | 뷰 `payment_attempts` | 구간 안 결제 시도 수 (`COUNT(*)`, PG별) |
| `pg_cause_failures` | 뷰 `payment_attempts` | `failure_cause = 'PG'` 건수 (PG별). R1의 주 신호 |
| `failure_rate` | 뷰 `payment_attempts` | 탐지가 계산. `attempts`가 N_min 이상일 때만 보조로 사용 |
| `kafka_msg_count` | 원장 `topic_messages` | 토픽별 `COUNT(*)` (`kafka_timestamp`로 묶음). 중복 전송도 세는 것이 맞다. **모든 메시지가 들어 있는 표는 `topic_messages`뿐**이라 누락(offset 빈틈)과 적재 중복은 이 표로만 판단한다. 같은 `payment_id` 중복은 정상(뷰가 걸러 줌) |
| `bronze_lag_msgs` | 원장 `bronze_lag_snapshots` | 토픽 전체 밀린 개수는 **합** (`SUM(lag_msgs)`) |
| `bronze_lag_sec` | 원장 `bronze_lag_snapshots` | 토픽 전체 밀린 시간은 **최댓값** (`MAX(lag_sec)`) |
| `bronze_report_gap` | 원장 `bronze_lag_snapshots` | 같은 토픽에서 측정 줄이 연속으로 없는 분 수. `committed_offset`이 멈췄는지, `connector_state`도 함께 본다 |
| `malformed_count` | 뷰 `malformed_messages` | **현재 `rule_version`만** 센 깨진 메시지 수 (토픽별). 오류 줄 수(`COUNT(*)`)로 세면 부풀어 보인다. 이 뷰의 한 줄에는 그 메시지의 오류 개수(`error_count`)와 (필드, 사유) 쌍 전부(`errors`)가 들어 있다 |

## 4. 탐지 규칙 (임계값은 모두 임시값, 가짜 데이터로 조정)

| 규칙 | 신호(이상으로 기록) | 같이 보는 것(다른 원인 지우기) | 시나리오 |
|---|---|---|---|
| R1 PG 원인 결제 실패 | 한 PG의 최근 15분 `pg_cause_failures` ≥ 3 **이고** `pg_cause_failures ÷ attempts` ≥ 20% (제안) | 같은 PG의 고객 원인 실패, 다른 PG, 같은 시간의 형식 오류·Bronze 지연 | 1. PG 장애 |
| R2 유입 증가 | **단독으로 이상을 기록하지 않음.** R3의 증거로만 사용 | `kafka_msg_count`가 평소보다 늘었는가 | (R3 보조) |
| R3 Bronze 소비 지연 | `bronze_lag_sec` ≥ 60초, 또는 측정 줄이 같은 토픽에서 연속 N분 없음 (프로토타입 기본 3분, 미정) | R2(유입이 늘었나), `malformed_count` | 2. 트래픽 폭주로 소비 지연 |
| R4 깨진 메시지 급증 | 한 토픽의 `malformed_count` ≥ 5 이고 깨진 비율 ≥ 5% | `malformed_events`의 필드·사유 분포, `kafka_msg_count` | (컨트롤러에 이 신호를 일으키는 사건이 아직 없음, 7절) |
| R5 한 주문에 성공 결제 2건 | 뷰 `payment_attempts`에서 `status = 'SUCCESS'`인 줄이 2건 이상인 주문이 최근 5분 사이 적재된 줄(`loaded_at`)에 1개 이상 (제안) | 같은 주문의 `attempt_no`와 시각, 중복 줄의 `loaded_at` | 3. 데이터 오염(성공 결제 중복) |

- R1은 `failure_rate`가 아니라 **PG 원인 실패 건수**를 주 신호로 쓴다. 하루 900주문 규모에서는 비율이 흔들려서, 건수가 안정적이다. (제안 · 가짜 데이터 30회 시험 결과)
- 시뮬레이터 확률표는 평소에도 PG 원인 실패가 시도당 약 1.15% 섞인다고 정했다. 이 값을 넣으면 **고정 "3건 이상"만으로는 주문이 많을수록 오탐이 크게 늘었다**(하루평균 5,000건에서 하루 4건, 저녁 피크 10건, 중간 모드 56건). 그래서 **"그 PG 결제 시도 중 PG 원인 실패 비율 20% 이상"을 함께 요구**하도록 바꿨고(제안), 모든 모드에서 30회 모두 탐지하면서 오탐이 하루 0.03~0.07건으로 돌아왔다. 20%는 시험으로 고른 값이다(10%는 오탐 1.2건, 30%는 탐지가 늦어짐). 한 PG의 실패율 90%인 장애만 시험했으므로 **일부만 실패하는 약한 장애는 놓칠 수 있다.** 근거 코드: `agent/prototype/modes.py`.
- R5는 형식은 맞고 **업무 규칙만 어기는 행**을 잡는다. 시뮬레이터 컨트롤러가 "한 주문에 성공 결제 2건"을 만들 때 새 행의 시각을 기존 성공 결제의 +2초로 넣어서 `completed_at`은 과거일 수 있다. 그래서 순찰은 **적재된 시각**으로 최근 5분을 본다. 비율 조건이 없어 3분을 기다리지 않는다. 실패한 뒤 재시도로 성공한 주문은 SUCCESS가 1건이라 세지 않는다. (제안)
- 같은 컨트롤러의 "주문 총액 ≠ 항목 합계"(`ORDER_TOTAL_MISMATCH`)는 **아직 규칙이 없다.** Gold B 원장에는 주문 금액이 없어서 Silver 쪽 검사가 필요하다. (**미정**, 9절)
- R3의 유입·지연 해석표: 지연↑·유입↑ = 사람이 몰려 밀림(시나리오 2), 지연↑·유입 평소 = Bronze 적재 자체 문제, 지연 평소·유입↑ = 잘 처리 중(이상 아님).
- 건수 규칙(R1, R3의 일부, R4의 건수)은 쌓이는 대로 바로 판정하고, 비율 규칙은 구간이 끝난 지 3분 지난 것만 판정한다. (결정)
- R1에 비율 조건이 생겼으므로 늦게 온 데이터가 비율을 낮출 수 있다. 은서 님 문서의 "비율 규칙은 3분 기다린다"를 적용해야 하는데, 프로토타입은 원장에 보이기까지 1분만 반영했다. 3분 대기를 넣어 다시 쟀고(허용 지연 표), 탐지 시간은 평균 7~8분(최대 10분)으로 늘었지만 오탐은 늘지 않았다.
- 판정 시점의 숫자를 다시 만들려면 `loaded_at ≤ 판정 시각`인 줄만 센다. (결정)
- `PROCESSING_ERROR` 구간처럼 **Gold B 자체 오류**는 이상 이력에 올리지 않고 따로 표시한다. 적재 잡이나 수집기가 2분 넘게 멈춘 것도 데이터 이상과 섞지 않는다. (제안)

## 5. `gold_b.anomaly` 컬럼 (제안)

**이상 이력은 지우거나 덮어쓰지 않고 판정 회차(`run_id`)마다 새 줄로 쌓는다.** "현재 보기"는 같은 시간대의 가장 최근 회차만 보여 주는 뷰로 만든다.

기본 키는 `(run_id, anomaly_id)`다. `anomaly_id = hash(rule_id, rule_version, scope_key, window_start)`로 만들어, 같은 규칙 버전과 같은 입력이면 같은 id가 나오게 한다(중복 방지). 규칙 버전이 id에 들어 있으므로 규칙을 바꿔도 옛 판정이 남아 비교할 수 있다.

| 컬럼 | 타입 | 뜻 | 예시 |
|---|---|---|---|
| `run_id` | STRING | 판정 회차 (판정 잡이 한 번 돈 단위) | `20261020T0115Z` |
| `anomaly_id` | STRING | 위 해시 | `a-7f3c…` |
| `rule_id`, `rule_version` | STRING | 어떤 규칙, 어떤 버전이 잡았나 | `R1_PG_FAILURES`, `v0.1` |
| `anomaly_type` | STRING | 이상 종류(신호) | `PG_FAILURE_SPIKE` |
| `source_table` | STRING | 읽은 원장·뷰 | `payment_attempts` |
| `window_start`, `window_end` | TIMESTAMP | 판정한 시간대 (UTC) | 15:00, 15:15 |
| `scope_type`, `scope_key` | STRING | 범위 | `pg`, `PG_A` / `topic`, `clickstream` |
| `metric` | STRING | 본 지표 이름 (3절의 이름) | `pg_cause_failures` |
| `observed_value` | DOUBLE | 관측값 | 7 |
| `baseline_value` | DOUBLE | 비교 기준 | 3 |
| `baseline_kind` | STRING | 기준 종류 | `FIXED_THRESHOLD` / `PREV_WINDOW` |
| `sample_size` | BIGINT | 판정에 쓴 건수 | 8 |
| `episode_start`, `episode_end` | TIMESTAMP, NULL 허용 | 연속된 시간대를 합친 이상 기간. 재처리 범위 후보 | 15:00, 15:20 |
| `evidence_ref` | STRING(JSON) | 조사가 볼 곳. 깨진 메시지는 `start_offsets`(파티션별 가장 이른 offset)를 포함 | `{"table":"malformed_events","topic":"clickstream","start_offsets":{"2":18342}}` |
| `status` | STRING | `OPEN` / `INVESTIGATING` / `REPORTED` | `OPEN` |
| `detected_at` | TIMESTAMP | 판정 잡이 기록한 시각 | 15:20:40 |

- 정답(`expected_*`)은 이 표에 넣지 않는다. 탐지는 신호까지만 말하고 원인은 조사가 찾는다.
- 시각은 UTC로 저장하고 화면에서 한국 시간으로 바꾼다.
- 재처리 전후 비교에서는 `detected_at`, `run_id`를 제외한다(실행 시각에 따라 달라지므로).

## 6. 재처리 뒤 재판정과 `reprocess_events`

원장은 재처리 때 **1시간 폴더 통째로** 교체된다(승인한 범위보다 넓을 수 있다). 교체가 끝나면 그 시간대를 다시 판정해야 한다.

- **합의(Gold B 담당 답변, 2026-10-18): 같은 Airflow 흐름에서 재처리가 끝나면 재판정이 바로 이어서 돈다.** 재처리 잡이 실제 교체 범위(1시간 폴더 단위라 승인 범위보다 넓을 수 있다)를 넘긴다. 재판정은 `LEDGER_REPLACED`가 찍힌 뒤에만 시작한다(교체 도중에는 폴더가 비어 있을 수 있다). **Airflow 연결 전까지는 임시로 5분마다 도는 판정 잡이 `reprocess_events`의 새 `LEDGER_REPLACED` 줄을 찾아 그 범위를 다시 판정한다.** Airflow에서 실제로 이어 붙이는 일은 플랫폼 담당 확인이 필요하다(**미정**).
- `LEDGER_REPLACED`는 **시간 폴더마다 한 줄씩** 쓴다(합의). 재판정은 줄마다 그 시간대를 다시 판정한다.
- 재판정 결과는 새 `run_id`로 쌓으므로 **옛 판정이 지워지지 않는다.** 이상이 사라졌다면 "현재 보기"에서 사라지고 이력에는 남는다.
- 재처리는 항상 원장 3개(`payment_events`, `topic_messages`, `malformed_events`)를 같이 교체한다. 일시 실패는 Airflow가 같은 승인 범위 안에서 **자동 재시도 2번**까지 하고(합의), 계속 실패하면 `FAILED`로 멈춰 사람이 다시 승인한다. 원본이 없는 구간은 재시도 없이 바로 `FAILED`다(합의).

`reprocess_events` 단계 (줄을 고치지 않고 단계마다 새 줄을 쌓는다. **현재 상태는 마지막 줄의 `step`**):

| step | 쓰는 사람 | 뜻 | 상태 |
|---|---|---|---|
| `REQUESTED` | 탐지(승인 화면) | 재처리 요청 (승인 범위) | 결정 |
| `APPROVED` / `REJECTED` | 탐지(승인 화면) | 사람이 승인 또는 거절 | 결정 (Gold B 문서에 반영됨) |
| `STARTED` | Gold B(재처리 잡) | 교체 시작 | 결정 (쓰는 것도 합의) |
| `LEDGER_REPLACED` | Gold B(재처리 잡) | 원장 시간 폴더 교체 끝 (실제 교체 범위, 폴더마다 한 줄) | 결정 |
| `REDETECTED` | 탐지(판정 잡) | 교체된 시간대 재판정 끝 | 결정 |
| `FAILED` | Gold B(재처리 잡) | 실패. `detail`에 이유 | 결정 (Gold B 문서에 반영됨) |
| `VERIFIED` | 탐지(판정 잡) | 재판정 결과로 문제가 해결됐는지 확인함 (해결 / 미해결) | 결정 (Gold B 문서에 반영됨) |

컬럼: `request_id`, `step`, `at`, `actor`, `reason`, `window_start`, `window_end`, `rule_version`(다시 계산에 쓴 규칙 버전), `source`(`KAFKA` / `BRONZE`), `attempt`, `parent_request_id`, `detail`.

## 7. 정답표 `incident_log`

시뮬레이터 컨트롤러(`simulator/src/sim/controller`, 설명은 `docs/tasks/sim-controller.md`)가 **이미 구현해서 main에 합쳐졌다.** 이 절은 그 실제 형식을 기준으로 한다. (초안은 8개 컬럼 표를 가정했으나 실제와 달라 바꿨다.)

| 항목 | 내용 | 상태 |
|---|---|---|
| 위치 | `s3://<버킷>/ground_truth/incident_log/` (로컬은 폴더) | 결정 (컨트롤러 구현) |
| 형식 | JSON. **사건 하나가 파일 두 개**: 시작(`start`) 기록과 끝(`end`) 기록. 파일명 `YYYYMMDDTHHMMSSZ_<incident_id>_<phase>.json` | 결정 (컨트롤러 구현) |
| 순서 | 장애를 바꾸기 **전에** 시작 기록을 먼저 남긴다 (기록이 실패하면 바꾸지 않는다) | 결정 |
| 시각 | UTC (`YYYY-MM-DDTHH:MM:SSZ`) | 결정 |
| 접근 | 조사 에이전트가 읽지 못하게 권한을 분리한다. 에이전트는 `gold_b/`만 읽는다 | 플랫폼 담당이 가능하다고 답함. 설정은 **미정** |

```json
{"schema_version": 1, "incident_id": "<uuid>", "phase": "start", "type": "PG_OUTAGE",
 "at": "2026-10-18T08:12:00Z", "params": {"pg": "PG_B", "extra_fail": 0.85, "planned_minutes": 10}}
{"schema_version": 1, "incident_id": "<uuid>", "phase": "end", "type": "PG_OUTAGE",
 "at": "2026-10-18T08:22:00Z", "ended_by": "timer", "result": {}}
```

- `ended_by`: `timer`(자동 복귀) / `manual`(버튼) / `shutdown` / `complete`(오염처럼 바로 끝나는 사건) / `failed`(적용 실패)
- 데이터 오염의 `start.params.kind`가 종류이고, `end.result`에 `affected_count`와 `order_ids`(최대 500개)가 들어 있다.
- 채점 스크립트(`agent/eval`)는 같은 `incident_id`의 start·end를 짝지어 `injected_start` = start의 `at`, `injected_end` = end의 `at`으로 쓴다.
- **정답 이상 종류, 정답 층은 정답표에 들어 있지 않다.** 사건 종류에서 채점 스크립트가 정한다(아래 표). 초안의 `expected_*` 컬럼은 쓰지 않는다.

| 컨트롤러 사건 | 정답 이상 종류 | 정답 층 | 정답 대상 | 탐지 규칙 |
|---|---|---|---|---|
| `PG_OUTAGE` | `PG_FAILURE_SPIKE` | 결제 | `params.pg` | R1 |
| `INGEST_LAG` (burst 모드) | `BRONZE_LAG_SPIKE` | 적재 | 모든 토픽 | R3 |
| `DATA_POLLUTION` / `DUPLICATE_SUCCESS_PAYMENT` | `DUPLICATE_SUCCESS_PAYMENT` | 데이터 품질 | 전체 | R5 |
| `DATA_POLLUTION` / `ORDER_TOTAL_MISMATCH` | (없음) | 데이터 품질 | - | **규칙 없음** (미정) |
| `TRAFFIC_SURGE` (medium 모드), `OPERATOR_PAUSE` | 채점하지 않음 | - | - | - |

- 장애는 **버튼 클릭으로 주입**한다. 시작 시각은 시작 기록의 `at`이고, 끝 시각은 끝 기록의 `at`이다(종료 시각 문제는 해결됐다).
- 사건 1 PG 장애는 기본으로 **실패율을 0.85만큼 더하고 10분(최대 60분)** 이어진다(`DEFAULT_PG_EXTRA_FAIL`, `DEFAULT_PG_OUTAGE_MINUTES`). 강한 장애다. 이것은 실제 결제 장애이므로 에이전트는 "데이터 문제가 아니다"라고 결론 내리고 재처리를 권하지 않아야 한다. (제안)
- 사건 2는 burst 모드(일상 피크의 10배, 15분 뒤 자동 복귀)다. 컨트롤러는 **주문을 늘려서 소비 지연을 노릴 뿐**이다. 실제로 Kafka 적재가 밀려 지연이 측정되는지는 아직 확인하지 않았다(**미정**, 확률표도 폭주만으로는 안 밀릴 수 있다고 적었다). medium 모드(3배)는 지연이 목적이 아닌 약한 급증이라 채점하지 않고, 이 구간에 울린 이상은 오탐으로 센다.
- **데이터 오염은 형식이 깨진 메시지가 아니다.** DB 제약은 통과하지만 업무 규칙을 어긴 행이다. 그래서 R4(깨진 메시지)로는 못 잡고, 성공 결제 중복은 R5가 잡는다. 형식이 깨진 메시지를 주입하는 사건은 컨트롤러에 없다.
- 오염은 원본 DB에 넣은 행이라 재처리(Kafka에서 원장을 다시 만듦)를 해도 그대로 다시 나올 수 있다. 이때 재판정은 `STILL_OPEN`이다. 승인·재처리 시연을 오염으로 할 수 있는지는 팀이 정해야 한다(**미정**).

## 8. 채점 (제안)

| 항목 | 기준 | 계산 |
|---|---|---|
| 탐지 적발 | 정답표의 `injected_start` 이후 **허용 지연** 안에 같은 사건에 대응하는 이상 이력이 있는가 | 적발한 사건 수 / 규칙이 있는 사건 수 (규칙이 없는 사건은 "규칙 없음"으로 따로 보고하고 분모에서 뺀다) |
| 오탐 | 주입 구간과 허용 지연 밖에서 생긴 이상 이력 건수 | 건수 |
| 층 판별 | 리포트의 원인 층 = `expected_layer`인가 | 맞은 사건 수 / 규칙이 있는 사건 수 |
| 근거 연결 | 리포트의 주장마다 근거(표·조회 결과)가 있는가 | 근거 있는 주장 비율 |

### 허용 지연 (제안, 팀 결정 대기)

판정을 5분마다 돌릴 때, 가짜 데이터로 30번 반복해 잰 "장애 시작부터 판정까지 걸린 시간"의 최댓값에 판정 주기 한 번(5분)을 더했다. **5분 여유는 임의 값이다.** 조건은 평소 PG 원인 실패 1.15% + R1에 비율 20% 조건 + 비율 규칙의 3분 대기다. 주문량은 시뮬레이터 확률표(하루 주문 약 5,000건은 **제안, 확정 필요**) 기준이다. 일상 모드는 하루 곡선을 따르므로 새벽과 저녁 피크를 나눠서 봤다.

| 사건 | 일상 새벽 (분당 0.7) | 일상 하루평균 (5,000건/일) | 일상 저녁 피크 (6.3) | 중간 (19) | 폭주 (63) |
|---|---|---|---|---|---|
| 1 PG 장애 | 25분 (측정 최대 20분) | 15분 (최대 10분) | 15분 (최대 10분) | 15분 (최대 10분) | 15분 (최대 10분) |
| 2 소비 지연 | 15분 (최대 10분) | 10분 (최대 5분) | 10분 | 10분 | 10분 |
| 3 성공 결제 2건(R5) | 10분 (제안값) | 10분 | 10분 | 10분 | 10분 |

- 확률표도 "새벽에는 분당 주문이 0.7건이라 장애는 **저녁 피크에 주입하는 게 안전**하다"고 적었다. 저녁이나 중간·폭주 모드에서 주입하면 사건 1은 15분, 사건 2·3은 10분으로 정할 수 있다.
- **이 표는 장애 중 PG 실패율이 90%인 강한 장애** 기준이다. 실패율이 50%이면 최대 15분, 30%이면 최대 25분이 걸리고, 20% 이하이면 일부를 놓친다(비율 기준 20% 때문). 시연 장애의 실패율을 정해야 이 표를 쓸 수 있다.
- 근거 코드: `agent/prototype/modes.py`. 프로토타입은 하루 내내 같은 주문 속도로 가정하고, 사건 2는 평소의 **20배** 유입 급증이라 시뮬레이터의 폭주 모드와 정의가 다르다.
- 사건 3(R5)의 10분은 **측정한 값이 아니다.** 비율 조건이 없어 3분 기다리지 않으니 적재 뒤 다음 순찰(최대 5분 뒤)에 잡힌다고 보고 5분 여유를 더한 값이다. 측정은 안 했다. (제안) 이전 초안의 "스키마 오염(R4)" 행의 측정값은 R4 기준이었다.
- 채점은 사건 끝 뒤 허용 지연의 2배(임의 값)까지 울린 이상을 그 사건의 것으로 보고, 허용 지연을 넘기면 "늦음"으로 센다. 오염처럼 순간에 끝나는 사건에서 "늦음"을 구별하려는 것이다.
- 판정이 5분마다 도므로 사건 2·3의 측정값은 5분 단위로 나온다. 5분보다 정밀한 값이 아니다.

## 10. 지난 초안에서 바뀐 것

- 집계 표(`payment_metrics`, `pipeline_health`)와 워터마크 → **원장 4개 + 정리 뷰 2개**, 구간 확정 없음
- R1: 비율 → PG 원인 실패 **건수**, R3: 측정 줄이 연속으로 없음 → 줄 수 기준, R4: 오류 줄 수 → **깨진 메시지 수(현재 규칙 버전만)**
- 이상 이력: 덮어쓰기 가능성 → **회차(`run_id`)별로 쌓기**
- 재판정: Airflow 자동 호출 → 재처리 잡이 교체 범위를 바로 넘김(Gold B 문서 합의). 이어 붙이기가 어려우면 판정 잡이 새 `LEDGER_REPLACED`를 확인하는 대안
- 허용 지연: 시나리오 1은 약 15분, 2·3은 약 7분(구간+워터마크 기준) → **시연 모드별 제안** (시뮬레이터 확률표 기준으로 다시 계산)
- 정답표: 위치·형식·사건 2 포함 여부 확정 → 8개 컬럼 가정을 버리고 **컨트롤러의 실제 start·end 기록 형식**으로 바꿈
- 시나리오 3: "스키마 오염(깨진 메시지, R4)" 가정 → 컨트롤러가 만드는 **업무 규칙 위반 오염**(성공 결제 중복은 R5로 추가, 주문 총액 불일치는 규칙 없음)
