# 담당 경계와 팀원 연결 계약

상태: 제안 · 실제 담당자 이름과 입력값은 미정 · 2026-10-14

## 역할 경계

루트 및 `infra/CLAUDE.md`의 협업 규칙을 따른다. 인프라 담당은 공용 실행 기반·노드 용량·AWS 권한을 관리한다. 팀원은 자기 애플리케이션 코드와 앱 수준 values를 관리한다. 하나의 Kubernetes 리소스/Helm release/CRD를 Terraform과 Argo CD 등 여러 도구가 동시에 소유하지 않도록 관리 주체를 명시한다.

| 영역 | 인프라 담당 | 데이터·앱 담당 | 공동 결정 |
|---|---|---|---|
| Kafka | 운영 기반, 네트워크/인증, 스토리지, 자원/복구 기반 | 토픽 의미·키·스키마, producer/consumer 코드 | 토픽 생성 담당·자동화 도구, partition·복제·보존·처리량 |
| Connect/Debezium | 런타임·이미지 배포 경로, Secret 전달, API 접근 통제 | 커넥터 설정, 캡처할 테이블/컬럼, snapshot·오류 처리 | 호환 버전, 내부 토픽, DB 계정·publication/slot 수명주기 |
| RDS CDC | 파라미터 그룹·SG·백업·WAL/용량 관측 기반 | 테이블·migration, 필요한 DB 권한 명세 | 전용 계정/권한 공급 주체, 재시작 시점, failover 후 복구 검증 |
| Consumer → Bronze | 이미지 실행 환경, Pod Identity·S3 권한·로그 | 소비/commit·재처리·파일 생성·중복 처리 | 저장 prefix, checkpoint/DLQ, 정상/실패 판정과 필요한 지표 |
| Spark → Silver/Gold | 실행 namespace·RBAC·스토리지 권한·용량 한도 | 변환 코드, 패키지/이미지, 잡별 자원 요구 | 실행 방식·동시 작업 수·checkpoint/임시 경로 |
| Airflow | 배포 기반, metadata DB 연결·Secret/로그·UI 접근 | DAG·연결 요구·앱 values, schedule·task 재시도 | executor·DAG 전달 방식·동시성·metadata 보존 |
| 모니터링 | 지표/로그 수집·저장·접근·인프라 알림 기반 | 업무 지표 노출, lag/품질/탐지 규칙의 의미 | 임계값·보존·수신처·장애 대응 담당 |
| 대시보드·에이전트 | 합의된 런타임·ServiceAccount·조회 권한 | UI·탐지·도구·원인 분석 로직 | API·인증·읽기 범위·서비스 자원 |
| CI/CD | 공용 검사, 배포 권한·환경·복구 절차 | 앱 빌드/테스트·이미지·앱 배포 설정 | 이미지 저장소, 승인/릴리스 및 GitOps 소유 범위 |

제네레이터 구현·빌드·실행 설정은 본 작업의 범위 밖이다. 부하 담당자가 제공하는 요구 처리량은 플랫폼 용량 산정의 입력으로만 받는다.

## 팀원에게 받을 최소 입력

값은 아래 표를 채워 관련 작업 지시서에 반영한다. 실제 비밀번호·토큰·AWS 계정 ID·엔드포인트는 공개 문서에 적지 않는다. 비밀 값 대신 참조 이름과 비공개 전달 경로만 합의한다.

| 대상 | 필수 입력 | 없을 때 보류할 구현 |
|---|---|---|
| 수집 담당 | Kafka 운영 요구, 예상 평균/피크 bytes/s와 메시지 크기, 보존 기간, 토픽 계약·partition 요구, 인증 클라이언트 | broker/스토리지/가용성 규모와 토픽 자동화 |
| CDC 담당 | DB 테이블·컬럼 allowlist, PII 제외 방식, snapshot 여부, publication/slot 소유자, 필요한 권한·플러그인 | DB 권한 및 커넥터 등록. `member_archive`를 포함한 전체 테이블 캡처 금지 |
| Consumer 담당 | 이미지 digest 또는 빌드 저장소, 실행 명령, 환경변수·Secret 키, 종료/health 동작, 자원·동시성, S3 경로/지표 | Deployment/Job과 IAM 정책 |
| Spark 담당 | 배치/스트리밍, 제출 방식, 이미지·패키지, driver/executor 요구와 최대 동시성, 입력/출력/checkpoint 경로 | 실행 기반과 노드 용량 |
| Airflow 담당 | 사용 여부, executor, DAG 전달 방식, DB·외부 연결/Secret 이름, 로그 저장, 동시성 | Airflow 설치 및 metadata DB 연결 |
| 대시보드·에이전트 담당 | 배포 대상/이미지, 포트·health 경로, 인증, 조회 대상과 읽기/쓰기 범위, 자원 요구 | 서비스 배포와 조회 권한 |
| 전체 팀 | 가동 시간, 허용 중단·유실/복구 목표, 예산, 담당자·알림 수신처 | HA·백업·로그 보존·노드 상한 확정 |

그림의 “토픽 6개”, “1분 마이크로배치”, “리뷰 예정”은 업무 요구의 근거다. 그림만으로 토픽 이름·partition 수·Kafka/Spark 실행 방식이나 추가 서비스의 설치를 확정하지 않는다.

## 인프라가 전달할 결과

- namespace·ServiceAccount·접근 역할, 팀원 권한과 접속 방법.
- 내부 서비스 이름/포트, 비민감 환경변수 및 Secret 이름/필수 키. 실제 주소는 비공개 경로로 전달.
- S3 prefix별 허용 작업, 이미지 저장소/배포 절차, 자원 한도와 변경 요청 방법.
- health·로그·지표 확인 방법, 배포 상태·복구 및 담당자 인계 기준.
- 구현/로컬 검증/실배포/통합 검증을 구분한 상태 기록.

## 완료 판정의 경계

인프라는 “Pod Running”만으로 파이프라인 성공을 선언하지 않는다. 플랫폼 실행과 권한은 인프라가 확인하고, DB 이벤트가 Kafka를 거쳐 올바른 Bronze 파일이 됐는지는 데이터 담당자와 함께 확인한다. Silver/Gold 결과의 정합성과 탐지 성능은 해당 담당자의 완료 조건이다.
