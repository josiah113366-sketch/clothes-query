# 작업 지시서: sim/member-live

> 상태: 진행 전 · 브랜치: `sim/member-live` · 이전 작업: `sim/member-baseline` · 다음 작업: `sim/cdc-local`

## 목표

**신규 가입을 계속 만들어 DB에 한 건씩 넣는** `sim member live` 명령을 만든다. 가입 속도는 **평상시**와 **폭주** 두 모드이고, 모드와 시작·멈춤은 **제어 신호**로 바꾼다.

이 브랜치가 끝나면 로컬에서 `sim member live`를 켜 두면 `member`에 가입이 한 건씩 쌓이고, 제어 신호 파일을 바꾸면 속도가 평상시 ↔ 폭주로 바뀌고, 프로세스를 껐다 켜도 같은 순서로 이어서 만든다. 신규 가입은 베이스라인과 **같은 회원 생성 함수**를 쓴다.

이 지시서는 **자기 완결형**이다. 설계 문서(`docs/design/*`)가 레포에 있으면 함께 읽되, **이 지시서와 어긋나면 추측하지 말고 묻는다.**

## 이번 작업의 특례 (사용자 결정, 다른 문서보다 우선)

- **커밋하지 않는다.** 파일만 만들고 테스트까지 진행한다. 커밋, push, PR은 사용자가 확인한 뒤 직접 한다. (루트 `CLAUDE.md`의 "단계마다 작은 커밋"보다 **이 줄이 우선한다.** 아래 "작업 순서"의 단계는 커밋 단위가 아니라 작업 순서다.)
- 줄바꿈(CRLF/LF)만 바뀐 파일을 고쳐야 하면 **git 기준(LF)으로 되돌린 뒤 편집**한다 (baseline 때와 같은 방식). 고치지 않는 CRLF 파일은 건드리지 않는다.
- Python 3.12 가상환경(`simulator/.venv`, WSL), 사용자 컴퓨터의 WSL Docker를 쓴다. `psql`은 없으므로 `docker compose exec postgres psql -U sim -d clothes`로 확인한다.
- **로컬 DB에만** 쓴다. RDS에는 접속하지 않는다.
- Debezium 없이 **DB 적재까지만** 확인한다. (CDC는 `sim/cdc-local`)
- 완료 확인 중 만든 신규 가입 행은 **확인 후 삭제**하고 건수를 보고한다 (아래 "완료 확인"). 베이스라인 10만 행은 건드리지 않는다.

## 동작

### 가입 한 건

1. 가입 시점의 **시뮬레이터 시각**(`signup_at`)을 시계에서 얻는다. 배속 1이면 실제 현재 시각(KST)이다.
2. **베이스라인과 같은 회원 생성 함수**로 회원을 만든다. `signup_at`, 난수, 지역 목록, 전화번호를 인자로 넘긴다. (함수는 고치지 않는다. 필요하면 아래 "함수 추가"만)
3. **INSERT 한 건 = 트랜잭션 한 건**(자동 커밋)으로 `member`에 넣는다. 여러 가입을 한 트랜잭션에 묶지 않는다. (나중에 Debezium이 가입 하나당 `c` 이벤트 하나를 내보내려면 이렇게 해야 한다.) 컬럼 목록에서 `created_at`은 뺀다.

### 도착 간격과 속도

- 가입은 **푸아송 과정**으로 도착한다. 다음 가입까지의 간격은 지수분포이고, 속도(초당 건수) λ = `하루 가입 수 × 모드 배율 × rate_multiplier(시각) ÷ 86,400`. 간격은 시뮬레이터 초 단위이고, 실제 대기 시간은 `간격 ÷ 배속`이다.
- 모드 배율: `normal` = 1.0, `surge` = 폭주 배율(기본 4.6).
- **모드가 바뀌면 남은 대기를 버리고 새 속도로 간격을 다시 뽑는다.** 지수분포는 과거를 기억하지 않으므로 이렇게 해도 통계가 맞다.
- 간격을 뽑는 난수(스케줄 난수)와 회원 값을 만드는 난수는 **서로 다른 줄기**로 분리한다.

### 같은 시드, 재시작해도 이어서

- k번째 신규 회원(k = 0, 1, 2, …)은 **`derive_seed(시드, "live", k)`로 난수를 다시 심고(reseed)** 만든다. 그래서 k번째 회원의 값(`member_id`, 이름, 지역, 나이대 등)은 **시드와 k만으로 정해지고** 앞의 회원이나 전화번호 재시도의 영향을 받지 않는다.
- 시작할 때 **k의 시작값 = `member`에서 `signup_at >= 베이스라인 끝(KST 2026-10-01 00:00)`인 행 수**다. 이렇게 하면 프로세스를 껐다 켜도 같은 순서로 이어진다. (탈퇴는 행을 지우지 않으므로 세는 값이 줄지 않는다.)
- **베이스라인과 겹치지 않아야 한다.** 베이스라인은 시드를 그대로 쓰므로 신규 회원은 반드시 `derive_seed`로 **다른 줄기**를 쓴다. 같은 줄기를 쓰면 베이스라인과 같은 `member_id`가 나온다.
- **시작 시각 보호:** 시작할 때 시뮬레이터 시각이 베이스라인 끝(10/1 KST)보다 이르면 오류로 멈춘다 (위 "k의 시작값"의 기준이 깨지므로).

### 전화번호

- 신규 회원의 전화번호는 무작위로 하나 뽑아 INSERT한다. **다른 회원과 겹치면** DB의 UNIQUE 제약이 막는다. 이때 오류의 제약 이름이 `member_phone_key`면 **같은 난수 줄기에서 새 번호를 뽑아 다시 시도**한다 (최대 10번, 넘으면 오류). 재시도에서는 **전화번호만 바꾸고** 나머지 값은 그대로 둔다.
- 번호를 확인하려고 `member`에서 전화번호를 읽어 오지 않는다. (PII를 읽지 않는다.)
- 다른 제약 위반(예: `member_pkey`)은 **재시도하지 않고** 오류로 처리한다.

### 제어 신호

회원 실행기는 컨트롤러 모듈을 import하지 않는다. 신호는 `common/`의 **인터페이스**로 받는다.

```python
@dataclass(frozen=True)
class ControlState:
    running: bool      # False면 가입 생성을 멈춘다 (프로세스는 살아 있음)
    mode: str          # "normal" | "surge"

class ControlSource(Protocol):
    def read(self) -> ControlState | None: ...   # 읽을 수 없으면 None (마지막 상태 유지)
```

- 구현은 **`FileControlSource`** 하나: JSON 파일을 읽는다. 기본 경로 `simulator/.local/control.json`, 예: `{"running": true, "mode": "surge"}`. 파일이 없거나 JSON이 깨져 있거나 값이 잘못되면 **마지막으로 읽은 상태를 유지**하고 한 번만 경고한다.
- 실행기는 **약 1초마다** 상태를 읽는다 (대기 중에도 짧게 나눠 대기하면서 읽는다).
- `running=false`면 가입을 만들지 않는다. 다시 `true`가 되면 이어서 한다 (새 간격을 뽑는다).
- 모드가 바뀔 때마다 `mode: normal → surge` 형태로 한 줄 출력한다.
- 시작할 때의 상태는 CLI 옵션(`--mode`)이다. 제어 파일이 있으면 그 값이 이후를 덮어쓴다.
- 이 파일 방식은 **로컬 개발용**이다. ECS의 다른 컨테이너(컨트롤러)가 쓰는 방식은 아직 정해지지 않았으므로, 파일 방식을 "확정된 전달 수단"처럼 문서에 쓰지 않는다.

### 시계

`common/clock.py`의 `SimClock`: 시작 시점의 실제 시각을 기준으로 `시뮬레이터 시각 = 시작 시각 + 배속 × 실제 경과 시간`. 항상 **시간대 정보가 있는 KST(+09:00 고정 오프셋)** 로 돌려준다. 테스트에서 바꿔 쓸 수 있게 **현재 시각과 대기를 주입**할 수 있게 만들고(가짜 시계), 가짜 시계는 대기하면 시간이 그만큼 흐른다.

배속이 1보다 크면 `signup_at`(시뮬레이터 시각)과 `created_at`(DB가 기록한 실제 시각)이 어긋난다. 설계가 알고 있는 점이고 정상이다.

### 종료와 오류

- `SIGINT`/`SIGTERM`(ECS가 보내는 종료 신호)을 받으면 **지금 하던 INSERT를 끝내고** 요약을 출력하고 종료 코드 0으로 끝낸다. 트레이스백을 내지 않는다.
- DB 연결이 끊기면(`OperationalError`) 1초, 2초, 4초… 최대 30초 간격으로 **다시 연결**한다. 오류는 PII 가리기를 거쳐 출력한다 (예외 종류와 `sqlstate`만).
- 연결이 끊긴 동안 만들어진 회원은 없다. 다시 연결되면 새 간격을 뽑아 이어간다.
- 가입 생성은 **한 번에 하나씩 순서대로**다. 쓰레드·비동기를 쓰지 않는다.

### 2. 회원 모듈 (`src/sim/member/`)

| 파일 | 내용 |
|---|---|
| `schedule.py` | 도착 간격 뽑기. `rate_multiplier(시뮬레이터 시각)`(지금은 항상 1.0)과 모드 배율을 곱해 속도를 정하고 지수분포 간격을 돌려준다 |

| `params.py` (수정) | `NORMAL_DAILY_SIGNUPS = 5000`, `SURGE_MULTIPLIER = 4.6`, `DEFAULT_SPEED = 1`, 제어 신호 확인 주기(1초), 전화 재시도 횟수(10), 재연결 대기 한계(30초) |
| `generate.py` (필요하면 추가만) | 번호 하나를 뽑는 순수 함수 `draw_phone(rng) -> str` (형식은 베이스라인의 전화번호 형식과 **같은 함수**를 쓴다). 기존 함수는 고치지 않는다 |
| `cli.py` (수정) | `live` 명령 추가 |

### 3. CLI

```
sim member live [--mode normal|surge] [--daily 5000] [--surge-multiplier 4.6]
                [--speed 1] [--duration SECONDS] [--max-signups N]
                [--control-file PATH] [--seed N]
```

| 옵션 | 환경 변수 | 기본값 | 설명 |
|---|---|---|---|
| `--mode` | `SIM_LIVE_MODE` | `normal` | 시작 모드 |
| `--daily` | `SIM_LIVE_DAILY` | 5000 | 평상시 하루 평균 가입 수 |
| `--surge-multiplier` | `SIM_LIVE_SURGE_MULTIPLIER` | 4.6 | 폭주 배율 |
| `--speed` | `SIM_LIVE_SPEED` | 1 | 시간 배속 (1 = 실시간) |
| `--duration` | — | 없음(계속) | **실제 시간** 기준 실행 초. 지나면 정상 종료 |
| `--max-signups` | — | 없음 | 이 건수만큼 만들면 정상 종료 |
| `--control-file` | `SIM_CONTROL_FILE` | `.local/control.json` | 제어 신호 파일 |
| `--seed` | `SIM_SEED` | 42 | 기본 시드 (신규 회원은 여기서 파생) |

시작할 때 출력(PII 없음): 대상 DB(`호스트:포트/DB이름`만), 시작 인덱스 k, 모드, 속도, 평상시 하루 가입 수, 폭주 배율. **`--yes` 확인 질문은 두지 않는다** (상시 실행 프로세스이고 로컬 전용이라는 점은 시작 출력으로 알린다). 단, 대상 DB의 호스트가 `localhost`/`127.0.0.1`이 아니면 **실행을 거부한다.** (RDS 접속은 인프라가 준비된 뒤의 별도 작업에서 열어 준다.)

**진행 출력:** 실제 시간 10초마다 한 줄 — 모드, 지난 구간의 건수와 초당 건수, 누적 건수, 현재 시뮬레이터 시각. 회원 값은 출력하지 않는다. 종료 시 요약(총 건수, 모드별 건수, 실행 시간, 재연결 횟수, 전화 재시도 횟수).

## PII 안전

baseline 때와 같다. 이번 작업에서 특히 확인할 곳:

- 진행 출력, 시작·종료 출력, 경고에 이름·이메일·전화·생년월일·해시가 없다.
- 전화번호 재시도는 제약 이름(`diag.constraint_name`)으로만 판단한다. 오류 메시지 본문(`str(e)`)과 `diag.message_detail`은 읽지도 출력하지도 않는다. 처리는 `common/db.py`의 오류 가리기를 거친다.
- 가입 한 건의 값을 로그에 남기지 않는다. 식별이 필요하면 `member_id`만 쓴다.

## 테스트

**단위 테스트 (DB 없이, 가짜 시계 사용, 기본 `pytest`에 포함):**

- **속도:** 평상시, 가짜 시계로 시뮬레이터 10일 → 건수가 50,000 ± 5σ 안 (푸아송, σ = √50,000)
- **폭주:** `surge`로 시뮬레이터 1일 → 평상시의 4.6배 ± 5σ 안
- **모드 전환:** 중간에 `normal → surge → normal`로 바꾸면 구간별 건수가 각 속도를 따른다
- **멈춤·재개:** `running=false` 동안 건수가 늘지 않고, `true`로 돌아오면 다시 늘어난다
- **재현성:** 같은 시드 + 같은 가짜 시계 + 같은 제어 순서 → 만든 회원 값과 시각이 완전히 같다
- **k번째 값의 독립성:** 시작 인덱스를 0으로 한 실행의 k번째 회원과, 시작 인덱스를 k로 한 실행의 첫 회원이 **같다** (재시작해도 이어짐)
- **베이스라인과 다른 줄기:** 같은 시드의 베이스라인 앞 N명과 신규 앞 N명이 `member_id`로 **겹치지 않는다**
- **`derive_seed`:** 같은 입력은 같은 값, 다른 입력은 다른 값. 기존 `SimRandom(seed)`의 결과가 이 브랜치 전후로 **같다** (베이스라인 재현성 해시 테스트가 그대로 통과)
- **`signup_at`:** 시간대 정보가 있고, 배속 1에서는 시계의 현재 시각과 같으며, 시작 시각이 10/1 KST보다 이르면 오류
- **전화 재시도:** `member_phone_key` 위반을 흉내 내면 새 번호로 다시 시도하고, 11번째 실패에서 오류. `member_pkey` 위반은 재시도하지 않는다
- **제어 파일:** 정상 값 반영 / 파일 없음·깨진 JSON·잘못된 값은 마지막 상태 유지(경고는 한 번만)
- **종료:** 종료 신호 흉내 → 정상 종료와 요약, 트레이스백 없음
- **재연결:** `OperationalError`를 흉내 내면 대기(1, 2, 4초…, 한계 30초) 후 다시 시도하고, 오류 출력에 PII 문자열이 없다
- **출력:** 진행·시작·종료 출력에 이름·이메일·전화 형식(`example.com`, `010-`)이 없다

**통합 테스트 (`@pytest.mark.integration`, 로컬 DB):**

- baseline 때처럼 `localhost`가 아니면 건너뛰고, **임시 스키마**에 `db/schema/*.sql`을 적용해 쓰고 지운다.
- 임시 스키마에서: 베이스라인 소량(2,000명) 적재 후 `live`로 200건(가짜 시계) → 행이 모두 DDL 제약을 통과하고, `status='ACTIVE'`, `signup_at`이 시작 시각 이후, 이메일·전화 중복 없음
- 껐다 켜기: 100건 → 종료 → 다시 시작해 100건 더 → 총 200건, 시작 인덱스가 100에서 이어짐, 중복 없음
- 건당 트랜잭션: 100건을 넣고 나서 `count(DISTINCT xmin::text)`가 100이다 (가입마다 트랜잭션이 따로라는 증거)

아래를 **실제로 실행**해서 결과를 보고한다.

- [ ] `ruff check .`, `ruff format --check .`, `pytest`(단위) 통과, `docker compose up -d` 후 `pytest -m integration` 통과
- [ ] baseline 재현성 테스트가 **그대로 통과** (이 브랜치가 baseline 결과를 바꾸지 않았다)
- [ ] `docker compose exec postgres psql -U sim -d clothes`로 현재 상태 확인: `SELECT count(*) FROM member;`(베이스라인 10만) 과 `SELECT count(*) FROM member WHERE signup_at >= '2026-10-01 00:00:00+09';`(0)
- [ ] **실시간 확인 (배속 1):** `sim member live --daily 86400 --duration 20`(초당 약 1건) → 약 20건, `SELECT max(abs(extract(epoch FROM created_at - signup_at))) FROM member WHERE signup_at >= '2026-10-01 00:00:00+09';` 가 **2초 이하**
- [ ] **평상시 속도 (배속 1440, 시뮬레이터 하루 = 실제 1분):** `sim member live --speed 1440 --duration 30` → 약 750건 (± 5σ)
- [ ] **모드 전환:** 다른 터미널에서 `echo '{"running": true, "mode": "surge"}' > simulator/.local/control.json` 후 같은 조건으로 30초 실행하면 평상시의 약 4.6배. 실행 중에 `normal`로 되돌리면 속도가 내려가고, 진행 출력에 `mode: surge → normal` 줄이 나온다
- [ ] **멈춤:** `{"running": false, "mode": "normal"}`로 바꾸면 건수가 늘지 않고, `true`로 바꾸면 다시 늘어난다
- [ ] **껐다 켜기:** 실행 → `Ctrl+C` → 종료 코드 0과 요약 출력, 트레이스백 없음. 다시 실행하면 시작 인덱스가 **이전 종료 시점의 건수**에서 이어지고 `member_pkey` 오류가 없다
- [ ] **중복 없음:** `SELECT count(*), count(DISTINCT email), count(DISTINCT phone), count(DISTINCT member_id) FROM member;` 네 값이 같다
- [ ] **건당 트랜잭션:** `SELECT count(*), count(DISTINCT xmin::text) FROM member WHERE signup_at >= '2026-10-01 00:00:00+09';` 두 값이 같다 (가입마다 트랜잭션이 따로다)
- [ ] **`sim member verify --expected <현재 행 수>`:** 신규 가입이 섞인 상태에서는 가입 기간(항목 5)과 일별·시간대별(항목 6, 7)이 의도대로 **실패할 수 있다** (베이스라인 기준 검사이므로). 실패한 항목과 이유를 **보고만** 하고 verify 코드는 고치지 않는다

- [ ] 확인 후 신규 가입 행 **삭제:** `DELETE FROM member WHERE signup_at >= '2026-10-01 00:00:00+09';` 실행 후 `SELECT count(*) FROM member;`가 **100000**으로 돌아왔다. 삭제한 건수를 보고한다
