# 퍼널 제한 범위 검증과 최종 백필·증분 배치

상태: 최종 배치 구현·로컬 통합 검증 완료 · PR 검토 및 운영 검증 대기

## 결정·승인 범위

- 10/25 추가 승인: 작은 시험에서 끝내지 않고 1회 처리량 축소 → 계산·저장·조회 확인 → 날짜별 백필·증분을 구현한다. 이후 정기 실행은 수동 유지로 확정했다.
- 10/25 PR 생성 승인: 검증한 코드와 업무 DAG 연결을 범위별로 커밋·push하고 main 대상 PR을 제출한다. 운영 배포·실제 업무 실행은 후속 단계다.
- 신규 원본은 기본 32개/128MiB/UTC 수집 날짜 한 묶음으로 제한한다. 세션 이력·기존 날짜는 보존하며 조회 성공 후 다음 묶음으로 진행한다. 배포·업로드·실제 DAG 실행은 사용자 검수 뒤 진행한다.

- 기존 24개 세션을 고정하고 완료 거래 manifest의 클릭 원본 목록 전체에서 해당 세션 이력을 찾는다. 미래/목록 밖 데이터의 완전성을 주장하지 않는다.
- 완료 Silver에서 연결 주문·상품·결제·주문 검사·주문별 품질을 확인한다. 원본 전체 INCOMPLETE를 PASS로 변경하지 않는다.
- 입력과 기대값은 로컬 무시 경로에 보관하고 manifest에 파일 해시·출처·범위를 고정한다. 개인정보가 포함된 입력은 Git에 넣지 않는다.
- 기존 4개 DAG 중 퍼널의 명시적 demo 모드로 실행한다. 시연 전용 출력만 쓰고 운영 R6·Gold 공개는 수행하지 않는다.
- 단계별 소요 시간·건수·바이트·실행 환경을 기록한다. 준비 원본 탐색 시간은 Spark 시간과 분리한다. Pod 메모리/CPU 관측이 없으면 미측정으로 표시한다.
- 구현·원본 읽기·로컬 검증만 수행한다. S3 업로드·EKS/DAG 실행·이미지 발행은 하지 않는다.

## 완료 확인

- 다른 파일·다른 날짜의 선택 세션 이력 포함, 원본 변경 및 다른 입력 혼입 거부.
- 기존 거래 재계산 없이 Spark 결과가 Python 기대값과 같고 Parquet 재조회도 일치.
- 운영 current·카탈로그·R6 공개를 갱신하지 않고, 일반 실행 계약은 보존.
- 단계 시간은 개별 시간과 누적 시간을 구분하며 실행 실패를 성공으로 기록하지 않는다.

## 작업 결과

- 고정 원본 996개/3,347,202,371 bytes/8,455,204행을 읽어 기존 24개 세션의 추가 이벤트 7건을 발견했다. 선택 클릭은 136→143건이며 식별 불가 행은 0건이었다. 원본 탐색 121초, 전체 로컬 입력 준비 128.796초를 별도 기록했다.
- 완료 거래 Silver에서 주문 8건·상품 25건·결제 시도 9건을 선택했다. 주문 검사 8건 모두 PASS, 주문별 품질 24행의 활성 오류 0을 확인했다. 원본 전체 INCOMPLETE는 그대로 보존했다.
- 독립 Python 기대값은 퍼널 상세/일별 각각 109행, 세션×상품 단계 도달 건수 조회 109·담기 34·주문 25·결제 25다. 고정 표본의 결과이며 전체 방문자의 전환율로 쓰지 않는다.
- 운영 Spark 4.2/Python 3.10.12 이미지에 현재 소스를 마운트해 네트워크 차단 local[2] 실행을 완료했다. Python 기대값·저장 Parquet 재조회 일치, 42.638445초. 입력 검증 0.089364초, 클릭 저장 14.806159초, 거래/상품 준비 11.909473초, 퍼널 계산/저장 13.964709초, 결과 검수 1.699822초다.
- 이 시간은 SparkSession 생성 이후이며 Pod/제출 대기와 마지막 JSON 쓰기는 제외한다. EKS 성능이 아니다. Pod CPU·메모리는 아직 관측하지 않아 NOT_COLLECTED/NULL이다.
- 새 시연 모드 및 기존 공개·재처리 회귀 29개가 Python 3.12와 운영 3.10에서 통과했다. 실제 Airflow 이미지에서 4개 DAG/모드 분기 시험 4개 통과. Ruff(py310), diff 검사 통과.
- 새 진입점은 pipelines/funnel_demo.py, 로컬 준비기는 pipelines/funnel_demo_prepare.py다. 기존 퍼널 DAG의 명시적 mode=demo만 새 진입점으로 보낸다. 일반 실행은 보존한다.
- R6 공개기는 demo에서 NOT_APPLICABLE, Gold 공개기는 시연 완료 결과만 검증한다. 운영 Glue/R6/Gold 완료 목록·current를 변경하지 않는다. 시연 Athena 조회 표/뷰는 아직 연결하지 않았다.
- 별도 시연 조회용 DDL/고정 run_id 조회 예시는 pipelines/gold_a/funnel_demo_tables.sql에 준비했다. gold_a_demo 명칭·권한을 배포 담당과 검수한 뒤 완료 결과에 대해서만 적용하는 초안이며 이번에 실행하거나 자동 등록하지 않았다.
- 준비된 실제 입력·요청 예시는 pipelines/gold_a/.local/funnel-demo-closed-20261025/에 보관한다(Git 무시). S3 요청/conf 예시는 미업로드다. 신규 demo 출력/고정 입력 권한은 인프라 확인이 필요하다.
- 이미지 빌드·발행, S3 업로드, EKS/DAG 실행, 커밋·push·PR은 수행하지 않았다. 승인 후 해당 순서로 운영 측정을 진행한다. 기존 다른 작업 브랜치의 커밋을 다시 만들거나 변경하지 않았다.

### 최종 백필·증분 구현

- funnel_incremental.py: 새 원본만 공통 규칙으로 정규화, 기존 Parquet 상태와 SQL 중복/충돌 검사, 영향 세션 재계산, 다른 세션·날짜 보존, Silver 클릭/상태 및 Gold 전체 스냅샷 저장·재조회.
- funnel_incremental_prepare.py: 수동 실행 시 현재 원본 목록·완료 거래·상품 seed 고정, 변경/삭제된 기존 파일 차단, 신규 입력 없음 판정, 불변 요청 생성. --write-s3 없이 업로드하지 않는다.
- funnel_control.py: 조건부 처리 위치 잠금/변경, Athena 동일 run_id 건수 검증, 다음 날짜/묶음 생성, 종료 확인 후 수동 잠금 해제. 조회 실패 시 처리 위치를 넘기지 않는다.
- Gold 공개기는 백필 중간 파티션을 완료 목록에 넣지 않고 마지막 묶음에서 노출한다. 기존 대시보드의 최신 결과를 부분 백필로 대체하지 않는다. 기존 DDL/고정 run_id 조회 계약 유지.
- 퍼널 DAG에 incremental 진입점·조회 성공 후 순차 재호출 연결. 수동 schedule=None 유지. 종료 메시지 콜백으로 다음 주소만 전달하여 pods/exec/XCom 사이드카가 필요하지 않다.
- 실제 Spark 4.2/Python 3.10 local[2], Driver 1GiB에서 두 날짜 백필, 다음 실행의 늦은 성공 결제, 늦은 클릭과 파일 간 정확한 중복을 검증했다. 독립 Python 전체 재계산과 상세/일별 109행 일치, 저장 Parquet 재조회 통과. 마지막 엔진 검수는 각 묶음 40.961/30.854/20.727초(로컬, EKS 추정치 아님).
- 요청·처리 위치·Athena 실패 게이트·기존 공개 회귀 34개가 운영 Python 3.10에서 통과했다. 현재 Airflow 이미지의 4개 DAG·진입점·실행 순서·종료 메시지 콜백 시험 6개 통과. Ruff(py310) 통과.
- 기존 Parquet 상태 병합과 Silver/Gold 전체 스냅샷 IO·일별 합산 비용은 남는다. 새 원본 형식 검사를 제한하는 방식이며 EKS 전체 데이터 성능이 확인됐다고 주장하지 않는다.
- 실제 운영에는 새 이미지/DAG와 Athena 검증 작업그룹·결과 경로 설정 및 역할 권한 확인이 필요하다. 실제 S3 저장·Athena 엔진 조회·EKS 백필, 커밋/push/PR/이미지 발행은 아직 하지 않았다. DB/R6 복구나 공통 규칙 변경 없음.
